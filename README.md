# Collab Agent

Flask API, MySQL, 정적 HTML/CSS와 JavaScript로 구성된 협업 요청·일정 조율 앱입니다.

## 폴더 구조

```text
backend/
  app/
    __init__.py          # Flask 앱 생성, 컨트롤러·미들웨어 등록
    config.py            # 환경 설정
    database.py          # DB 연결·트랜잭션
    middleware.py        # 인증, 오류 응답, 응답 헤더
    controllers/         # HTTP 요청·응답과 API 경로
    services/            # 업무 규칙과 트랜잭션 경계
    repositories/        # SQL 조회·저장
    shared/              # 오류, 날짜, 직렬화, 입력 검증
  sql/schema.sql         # 테이블 정의
  server.py              # 개발 서버·Gunicorn 진입점
  requirements.txt
  Dockerfile
static/
  html/
    index.html           # 앱 공통 레이아웃
    pages/               # auth, requests, calendar, schedules, history 화면
    components/          # 재사용 HTML 템플릿
  js/
    app.js               # 초기화와 앱 이벤트 연결
    core/                # 공유 상태, API 통신, 라우팅
    pages/               # 화면별 렌더링과 사용자 동작
    components/          # 사이드바 등 UI 컴포넌트
    shared/              # DOM, 상수, 템플릿, 알림, 표시 도구
  css/styles.css
deploy/nginx/default.conf
tests/                   # DB 없이 실행하는 백엔드·프론트엔드 점검
compose.yaml
Dockerfile               # 정적 웹 서버 이미지
```

## 실행

프로젝트 루트의 `.env`에 `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`을 설정합니다.

```sh
docker compose up -d --build
```

브라우저에서 <http://localhost:8080>에 접속합니다. DB 테이블과 데모 데이터가 필요한 경우 아래 명령을 별도로 실행합니다. 기존 업무 데이터는 삭제하지 않습니다.

```sh
docker compose exec api python server.py init-db
```

```sh
docker compose ps       # 실행 상태
docker compose stop     # 종료
docker compose start    # 다시 시작
```

백엔드만 로컬에서 실행하려면 루트에서 다음 명령을 사용합니다. 화면과 API를 함께 사용하려면 위 Docker Compose 구성을 사용합니다.

```sh
python -m pip install -r backend/requirements.txt
python backend/server.py
```

## 모듈 수정 규칙

- API를 추가할 때 컨트롤러는 요청과 응답을 처리하고, 서비스는 업무 규칙을 처리하며, 저장소는 SQL을 담당합니다.
- 서비스에서 트랜잭션을 시작하고, 저장소 함수에 같은 커서를 전달합니다.
- 프론트엔드는 브라우저 기본 ES 모듈을 사용합니다. 필요한 함수와 상수는 `import`하고, 공유 데이터는 `core/state.js`의 `state`를 통해 읽고 씁니다.
- HTML 템플릿을 추가하면 `shared/templates.js`의 파일 목록에 등록합니다.
- 기존 HTML의 인라인 이벤트에서 호출하는 함수는 `core/template-actions.js`에서 명시적으로 연결합니다. 이 파일만 템플릿용 함수를 `window`에 노출합니다.
- 배포 경로나 정적 파일 경로를 바꾸면 Dockerfile, `.dockerignore`, Nginx 설정, 템플릿 경로도 함께 확인합니다.

## 검증

백엔드 의존성과 Node.js가 설치된 환경에서 프로젝트 루트에서 실행합니다.

```sh
python -m unittest discover -s tests -p "test_*.py"
node --experimental-vm-modules tests/frontend-smoke.cjs
docker compose config --quiet
```

프론트엔드 점검은 간단한 DOM·API 대역으로 모듈 연결, 초기화, 주요 화면 렌더링, 로그인 이동을 확인합니다. 실제 브라우저 표시와 MySQL 연동 확인은 별도 실행 환경이 필요합니다.

## 목업 사용 흐름

1. 요청자 계정에서 새 협업 요청을 열고 자연어 요청을 작성한 뒤 **요청 분석**을 누릅니다.
2. 업무 내용·마감·수행자를 확인하고, 빠진 규격 등의 정보를 입력합니다. 추가 답변을 반영해 다시 분석할 수 있습니다.
3. 추출된 조건과 직접 추가한 조건의 값을 확인한 뒤 제출합니다. 수량·규격은 해당 업무에서 필요한 경우에만 사용합니다.
4. 수행자는 받은 요청에서 먼저 일정 분석을 확인한 뒤 수락·조건부 수락·거절을 선택합니다. 조건부 수락 시 유지할 조건이나 기타 의견을 남깁니다.
5. 대안 생성 버튼은 AI 없이 고정 시연안 3개를 준비하며 대안3은 반드시 관계자 동의가 필요합니다. 날짜를 나눈 작업, 조건 변경 제안, 팀 업무 분담, 낮은 우선순위 업무 순연을 요청에 맞게 판단합니다. 서버에서 형식·담당자 권한·일정 충돌을 검증합니다. HARD와 유지하기로 선택한 조건을 보존하고 조정 가능한 SOFT 조건을 검토합니다. 기존 일정과 충돌하는 안이나 조건을 위반하는 안은 저장하지 않습니다. 서로 다른 대안 3개를 충족하지 못하면 저장하지 않습니다.
6. 요청자와 수행자가 각각 복수 선택 후 선택완료를 누릅니다. 양측 모두 완료하면 요청자가 공통 대안 중 하나를 지정하고 양측이 최종 확인합니다. 양측 최종 확인이 끝난 시점에 선택된 대안의 관계자 동의 요청만 자동으로 전달됩니다. 최종 확인 박스 안에서 동의 요청 전·대기·완료·거부 상태를 확인합니다. 선택완료 후에는 해당 사용자의 선택 변경을 화면과 서버에서 차단합니다. 변경이 필요하면 재조정으로 새 회차를 시작합니다.
7. 업무 분담자는 자기 요청함에서 동의·거부합니다. 기존 일정 순연은 영향을 받는 기존 요청자의 동의도 필요합니다. 동의 전에는 확정되지 않습니다.
8. 합의 확정 시 최신 일정으로 다시 검증하고 일정 변경과 작업 등록을 같은 트랜잭션에서 처리합니다. 거절된 요청은 새 마감·사유로 재요청하거나 취소할 수 있습니다.

재조정 시 이전 회차와 수정 의견을 보존하고 수행자의 수용 조건을 다음 회차로 넘깁니다. 의견 중 `3개 가능`, `분담 불가`, `순연 불가`, `11월 10일부터`, `11월 13일로 마감 변경` 같은 표현을 다음 계획에 반영합니다.

### HARD·SOFT 및 실제 AI 동작

요청 분석·요청서 작성은 서버의 OPENAI_API_KEY와 OPENAI_MODEL 설정으로 실제 AI를 호출합니다. 대안 생성은 AI를 사용하지 않으며 대안1·대안2·대안3의 고정 시연안을 만듭니다. 대안1·2는 수행자 단독 진행, 대안3은 실제 관계자 참여 또는 확인 동의가 필요한 안입니다. 수량이 1개여도 관계자 참여 안을 만들며 전체 수량과 HARD 조건을 유지합니다. 대안 생성은 빈 시간·HARD 마감·일정 충돌 때문에 차단하지 않습니다. 대안1·대안2·대안3(관계자 필요)을 고정 표시하며, 최종 확인과 관계자 동의 후 등록 단계에서도 기존 일정 충돌·작업 시간·마감에 따른 실행 가능성 검사는 하지 않습니다. 같은 팀 분담자가 없으면 다른 활성 직원의 관계자 확인을 요청하며, 존재하지 않는 계정은 만들지 않습니다. 구성은 공식 Responses API의 구조화 응답 형식을 따릅니다.

조건 기본값은 HARD입니다. HARD 조건과 수행자가 유지하기로 선택한 조건은 대안에서도 유지해야 하며, 선택하지 않은 SOFT 조건만 조정할 수 있습니다. 요청 상세의 조건 상자에 HARD·SOFT를 표시하고 클릭하면 상세 내용을 보여줍니다. 조건부 수락 팝업에는 모든 조건과 등급을 표시하고 유지할 수 있는 조건을 복수 선택할 수 있습니다.

일정·분담·관계자 동의·양측 최종 확인과 등록 전 우선순위·작업량 선택은 조건 제거 전 방식으로 복원했습니다. 요청자도 협업 진행 일정 등록 대상이며, 관계자는 본인의 동의 시 우선순위·작업량을 선택하면 다른 참여자 응답과 무관하게 본인 일정이 즉시 등록됩니다. 요청자·수행자의 나머지 설정과 전체 협업 완료는 기존 절차를 따릅니다. 실제 수행 업무와 진행 현황 일정은 구분합니다.

코드는 당시 실행 이미지와 제거 직전 기능을 기준으로 복구했습니다. 협업·조율·합의는 before-condition-class-removal 백업을 기준으로 복구하고, 응답·일정·첨부·확인 표시는 추가 백업으로 보완했습니다. 복구 직전 상태는 .local의 ZIP과 DB 백업으로 보관합니다.

조건부 수락 제출 직후 같은 화면에서 AI 대안을 바로 생성할지 확인합니다. 예를 선택하면 즉시 생성하고, 아니요를 선택하면 생성 버튼을 통해 나중에 실행합니다. 선택완료 전에는 대안 카드 전체를 눌러 본인 계정의 선택 상태를 전환할 수 있으며 상대방의 선택은 바꾸지 않습니다. 선택완료 후에는 잠깁니다. 카드에는 마감·총수량·담당 인원, 변경 제안과 경고를 표시합니다. 재조정 의견은 상세 화면의 팝업으로 작성하며 제출 실패 시 입력을 유지합니다.

관계자 동의 요청은 `/requests/consents` 및 협업 요청함 하위 메뉴에서 확인합니다. 요청 카드의 제목은 대안명이 아닌 협업 요청 제목입니다. 요청 전 상태의 동의 항목은 관계자에게 노출하지 않으며, 양측 확인 전이나 선택하지 않은 대안에는 직접 응답할 수도 없습니다. 로그인 화면에서는 5명의 이름별 계정 버튼으로 아이디·비밀번호를 자동 입력할 수 있습니다.

협업 완료는 자동으로 처리합니다. 양측 최종 확인 후 필요한 관계자가 모두 동의하면 동일 트랜잭션에서 일정 검증·등록, 관계자 기존 일정 순연, 요청 완료와 회차 종료를 처리합니다. 관계자가 필요 없는 경우 두 번째 최종 확인 시 즉시 완료합니다. 추가 확정 버튼은 표시하지 않습니다. 요청자와 작업이 직접 배정되지 않은 관계자에게는 협업 진행 기간을 표시하는 일정을 등록하며, 이 진행 현황 일정은 가용 시간 계산을 막지 않습니다.

자동 등록·변경된 일정은 계정별 `schedules.is_new`로 관리합니다. `GET /api/schedules/notifications`는 로그인 계정의 미확인 일정 수를 반환하고, `POST /api/schedules/notifications/read`는 표시된 일정 ID 중 본인 일정만 확인 처리합니다. 새 협업 일정은 보라색으로 깜빡이며 캘린더를 여는 것만으로는 확인 처리하지 않습니다. 해당 일정의 상세를 클릭해 성공적으로 불러오면 본인 일정 1건만 확인 처리하고, 이어진 모든 날짜 막대의 강조를 함께 해제합니다. 남은 미확인 일정이 있으면 사이드바 New는 유지됩니다. 다른 달의 미확인 일정과 다른 계정의 표시는 유지합니다. 화면이 활성화된 동안 20초 간격으로 새 상태를 확인하며 입력 팝업이나 처리 중인 작업은 방해하지 않습니다. 기존 DB는 `docker compose exec api python -m app.maintenance.migrate_schedule_notifications`로 `is_new` 항목을 추가합니다. 기존 일정의 내용과 확인 상태는 보존됩니다.

관계자 동의 전용 화면에서는 요청 제목을 펼쳐 협업 요청문, 요청자·수행자, 현재 요청 조건, 양측 조율 의견과 확인 시각, 최종 대안·합의 조건·전체 작업 일정, 본인의 업무 배정 또는 일정 변경을 확인한 뒤 응답합니다. 오른쪽 요청함 요약 상자는 기존 간단한 표시를 유지합니다. 상세 조회 `GET /api/consents/<id>`는 실제로 해당 동의 요청을 받은 직원에게만 허용하며, 양측 확인 전·선택하지 않은 대안·취소되거나 재조정으로 무효화된 요청은 차단합니다. 일반 협업 상세의 요청자·수행자 권한은 확대하지 않습니다.

관계자 동의 거부 시 사유를 필수 입력하며, 요청자·수행자의 요청 카드에 재조정 필요 배지와 협업 상세 상단에 거부자·사유를 표시합니다. 활성 화면에서는 주기적 갱신으로 새 거부 사실을 안내합니다. 같은 대안의 다른 미응답 동의 요청은 중단하며 거부된 대안의 선택 변경·확정은 차단합니다. 요청자 또는 수행자가 재조정 시작을 누르면 이전 대안·최종 확인 결과·조율 의견을 회차 기록에 보존하고 새 회차를 만듭니다. 재조정 시 거부 기록을 유지하고 분담을 거부한 직원은 시연 분담안에서 제외합니다. 생성 실패 시 새 회차와 거부 맥락을 유지해 수동 재시도할 수 있습니다. 같은 이전 회차에 대해 양측이 중복으로 재조정을 시작하지 못하도록 회차 ID를 검증하며, 새 대안은 다시 양측 선택완료·최종 확인과 필요한 관계자 동의를 거칩니다.

협업 상세의 수행자 일정 제목 옆 내 일정 버튼은 독립된 월별 캘린더 팝업을 엽니다. URL과 요청 상세, 기본 캘린더의 표시 월은 유지하며 팝업 안에서 월 이동·일정 상세 조회·본인 일정 수정/삭제가 가능합니다. 팝업에서도 일정을 직접 클릭한 경우에만 확인 처리하고, 이동·로그아웃 시 팝업과 중첩된 일정 상세를 닫습니다.

김민지↔이서준 중심의 별도 시연 초기화는 `python -m app.maintenance.reset_pair_scenarios --apply`로 구성합니다. 이 명령은 기존 협업·응답·협상·결과·협업 생성 일정을 삭제하므로 먼저 백업해야 합니다. `--apply` 없이 실행하면 같은 처리와 모든 대안을 검증한 뒤 되돌립니다. 일반 직원 일정은 유지하며, 기존 합의로 이동된 일정은 이후 수동 변경이 없을 때만 복원합니다. 응답 대기, 수락 완료, 대안 선택, 최유진 분담 동의 대기, 정하은 거부 후 재조정, 박지훈 기존 업무 순연 동의의 6가지 상황을 넣습니다. 박지훈은 기존 업무 요청자로 참여하며 타 부서에 제작 업무를 분담하지 않습니다. 기존 업무 순연 테스트를 위해 이서준 소유의 낮은 우선순위 업무 1건을 추가합니다. 사전 작성된 목업 대안은 DEMO_SCENARIO로 표시하며 실제 사용자의 새 대안 생성은 고정 시연안을 사용합니다.

시연 요청의 제목에는 업무명만 저장하고, 시연 번호는 원문에 보존하여 요청 카드·상세·합의 기록에서 작은 별도 표시로 보여줍니다. 진행 상태는 실제 데이터에 따른 배지로 표시하며, 양측 확인 후 관계자 응답을 기다릴 때는 관계자 동의 대기, 거부가 있으면 재조정 필요를 표시합니다. 제목에 상태를 고정해 두지 않아 진행 후에도 오래된 상태 문구가 제목에 남지 않습니다.

일정 자동 등록 전 참여자는 우선순위·작업량을 직접 선택합니다. 관계자가 없으면 양측 최종 확인에서, 관계자가 있으면 전원 동의 후 각 참여자가 설정합니다. 기존 일정 순연은 원래 우선순위·작업량을 유지합니다.

협업 요청 제목은 사용자가 처음 입력하며 AI 분석으로 덮어쓰지 않습니다. 조건 등급은 없으며 입력한 값은 현재 요청 조건으로 보존합니다. 요청 제출 시 문서·이미지·ZIP 첨부를 최대 5개(개별 10MB, 총 20MB) 저장할 수 있습니다. 파일은 인증된 다운로드로만 제공하며 요청자·수행자 또는 해당 협업의 동의 요청을 받은 관계자만 접근할 수 있습니다. 첨부 내용은 자동으로 AI에 전송하지 않습니다. 기존 DB는 python -m app.maintenance.migrate_request_extras로 첨부 및 계정별 확인 상태 테이블을 추가합니다.

받은 요청·나의 요청·관계자 동의 요청은 계정별 미확인 버전을 추적해 각각 New를 표시하며 하나라도 미확인이면 상위 협업 요청함에도 New가 표시됩니다. 상태가 바뀐 항목은 은은하게 깜빡이고 상세를 실제 확인하면 표시를 해제합니다. 읽은 버전 이후 변경은 다시 New가 되며 다른 계정의 확인 상태는 바꾸지 않습니다. 보낸 요청 상세에서는 수행자 일정 영역을 표시하지 않습니다.

관계자 없는 협업은 양측 최종 확인 시 내 일정 설정을 받고, 관계자가 있으면 최종 확인 단계에서는 받지 않습니다. 관계자는 동의 버튼에서 본인 일정 설정을 제출하면 즉시 본인 일정이 등록됩니다. 다른 관계자 동의나 요청자·수행자의 설정을 기다리지 않습니다. 전원 동의와 나머지 설정이 끝나면 전체 협업을 완료하며 이미 등록한 관계자 일정은 중복 생성하지 않습니다. 동의 거부나 재조정으로 해당 합의가 중단되면 선등록 일정을 정리합니다.

HARD·SOFT 제거 이후 변경은 복구되었습니다. 원래 요청 조건을 임의로 바꾸지 않으며 양측 확인과 필요한 관계자 동의를 거쳐야 등록합니다.

목업 일정 등록은 기존 업무 중복, 근무 시간, 이미 지난 마감을 이유로 차단하지 않습니다. 직접 수락한 요청의 마감이 이미 지났다면 현재 시각부터 10분의 시연 기간으로 등록합니다. 사용자 동의·계정 권한·우선순위와 작업량 입력 및 중복 등록 방지는 유지합니다.

현재 케이스명 기준 시연 데이터는 python -m app.maintenance.reset_named_scenarios --apply로 초기화합니다. 기존 협업·연결 일정을 삭제하므로 실행 전 백업해야 합니다. --apply 없이 실행하면 검증 후 되돌립니다. 제목은 테스트(응답 대기) 등의 형식으로 11건이며 김민지·이서준만 요청자/수행자입니다. 나머지 세 계정은 관계자로 참여합니다. 관계자 일정 선등록 케이스는 정하은 동의 및 일정 등록 완료, 박지훈 응답 대기 상태입니다. 일반 직원 일정은 유지합니다.
